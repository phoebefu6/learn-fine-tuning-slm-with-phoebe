Learn Fine-tuning and Small Language Models with Phoebe · Session 4 of 6

LoRA and QLoRA without the maths fear

LoRA has a reputation for linear algebra, and the reputation is bigger than the idea. You leave the model's weights exactly as they are, put two thin matrices beside each one, and train only those. QLoRA does the same thing on a base model squeezed to 4 bits so it fits on one modest GPU. Tonight we draw the one equation, read every knob in a real config against the docs, and work out by hand whether Larkline's tune fits on a 24 GB card before anyone presses train.

Part 1 · covers full fine-tune vs PEFT

Freeze the weights, train two thin matrices

5 min live

A full fine-tune updates every weight in the model, so you need memory for every weight, its gradient and its optimizer state, and you end up with a whole new copy of the model. Parameter-efficient fine-tuning (PEFT) leaves the original weights untouched and trains a small add-on. LoRA, from Hu et al. 2021 (arXiv:2106.09685), is the add-on almost everyone uses: it freezes the pre-trained weights and injects trainable rank decomposition matrices into each layer. That sentence sounds hard. The picture is not.

LiveThe one equation, read as a picture3 min▶

Take one weight matrix W inside the model, d rows by d columns. Normally the layer computes Wx. LoRA adds a second path: A squeezes the d input values down to just r numbers, B expands those r numbers back up to d, and the result is scaled by alpha divided by r. The layer now computes h = Wx + (alpha/r)·BAx. W is frozen: no gradient, no optimizer state, no change. Only A and B train.

The "low rank" in the name is the width of that squeeze. If r is 16 and d is 3,072, the trainable path carries 16 numbers where the full matrix has 3,072 columns. The bet is that the change a narrow task needs is small and structured enough to pass through that narrow pipe. For Larkline's six queues, that is a reasonable bet; session 5 checks it.

One detail matters on day one. In the PEFT library, B is initialised to zero by default (init_lora_weights=True), so BAx is zero before training. A freshly attached adapter changes nothing: the model behaves exactly like the base until the first update. And because BA can be added into W after training, Hu et al. 2021 report no additional inference latency once merged, unlike earlier adapter designs that added extra layers.

Live"10,000 times fewer parameters", read fairly2 min▶

The LoRA abstract says that compared with GPT-3 175B fine-tuned with Adam, LoRA reduces the number of trainable parameters by 10,000 times and the GPU memory requirement by 3 times, with quality on par or better on RoBERTa, DeBERTa, GPT-2 and GPT-3. Every part of that sentence is true, and it is true for that comparison.

The 10,000 figure depends on the size of the model and on r. On a 4B-class model with a larger r and more target modules, the ratio is much smaller (Part 2 works one matrix by hand). And notice the two numbers differ: trainable parameters fall by four orders of magnitude, memory by three times. The frozen weights still have to sit in GPU memory, and the activations still have to be computed. That gap is exactly why QLoRA exists (Part 3).

Self-studyThe disagreement: LoRA learns less and forgets less3 min▶

Hu et al. 2021 report LoRA on par with or better than full fine-tuning on their tasks. Biderman et al. 2024, "LoRA Learns Less and Forgets Less" (arXiv:2405.09673), tested harder targets: on code and maths, LoRA substantially underperformed full fine-tuning in standard low-rank settings. They also found the other half of the trade: LoRA better maintained the base model's performance outside the target domain, and full fine-tuning learned weight changes of rank 10 to 100 times higher than typical LoRA settings.

Both papers are right in their settings, and neither settles your task. A routing task with six labels sits much closer to "learn a narrow behaviour" than to "learn a new programming skill", which favours LoRA, but that is a reason to expect, not a result. The honest plan is to measure two things after the tune: the target task, and what the model used to do well. Session 5 builds both checks.

Real world

An adapter that starts as a no-op is a safety feature. Because the PEFT default sets B to zero, attaching a LoRA adapter to a production model and running your eval before training should reproduce the base model's scores exactly. If it does not, something in your pipeline is wrong (a different tokenizer, a different prompt template, a different decoding setting) and you have found it before spending a single GPU-hour.

Part 2 · covers the LoraConfig knobs

Six arguments, read against the docs

5 min live

A LoraConfig has many arguments and six that matter on day one. The Hugging Face PEFT reference gives each a default: r 8, lora_alpha 8, target_modules None (chosen by the model's architecture), lora_dropout 0.0, bias "none", and use_rslora False. Read them in that order and the config stops being a wall of numbers.

Liver and lora_alpha: the size of the pipe and the volume knob3 min▶

r is the rank, the width of the squeeze; the PEFT docs call it the "Lora attention dimension". For a d x d matrix, A has r x d values and B has d x r, so the trainable count is 2 x r x d and the trainable fraction is 2r/d. On an illustrative 3,072 x 3,072 matrix (a size picked for teaching, not read from any model card), r = 16 gives 98,304 of 9,437,184 values, 1.04 percent; the default r = 8 gives 0.52 percent.

lora_alpha sets how loudly the adapter speaks. The adapter's output is multiplied by lora_alpha / r, so r = 16 with lora_alpha = 16 gives a scaling of exactly 1.0, and the default 8 / 8 also gives 1.0. Set use_rslora=True and the scaling becomes lora_alpha / sqrt(r) instead: for 16 / 16 that is 16 / 4 = 4.0. That is the rank-stabilised variant; the point to remember is that changing r silently changes the scaling unless you change alpha with it.

Self-studytarget_modules, lora_dropout and bias3 min▶

target_modules decides which matrices get an adapter. The default None lets PEFT choose by architecture. The string "all-linear" targets all linear layers except the output layer, which is a common, simple choice for small models: more matrices adapted, more trainable values, more capacity. The trainable fraction per matrix is still 2r/d; the total depends on how many matrices and their real shapes, which you read from the model, not from a slide.

lora_dropout (default 0.0) randomly drops some of the adapter's input during training, a light regulariser for small datasets; 0.05 is a common small value. bias (default "none") says whether bias terms train too; leave it at "none" unless you have a reason. Neither changes the memory picture much. Both are worth writing on the run card, because "I changed dropout" is a classic reason two runs disagree.

Self-studyWhy adapters run a hotter learning rate2 min▶

The TRL SFTTrainer docs include a tip: adapters typically use a higher learning rate, about 1e-4. The SFTConfig default is 2e-5, set for full fine-tuning, along with 3.0 epochs. If you attach a LoRA config and forget to raise the rate, the run may learn very little and you may wrongly conclude LoRA "does not work" on your task.

Treat 1e-4 as the docs' starting point, not a tuned value. The rate that works for Larkline is whatever gives the best held-out score in session 5, and that search costs runs, which is why the run card exists.

Real world

Two defaults that disagree. The TRL documentation's own SFTConfig default learning rate is 2e-5, while its PEFT tip says adapters typically use about 1e-4, five times higher. Neither is wrong: one default serves full fine-tuning, the other is advice for adapters. The lesson travels to every library: read the tip next to the default, and write the value you actually used on the run card.

Part 3 · covers QLoRA and GPU memory

QLoRA: the same adapter on a 4-bit base

5 min live

LoRA shrinks what trains, but the frozen base still has to sit in GPU memory at 16 bits. QLoRA, from Dettmers et al. 2023 (arXiv:2305.14314), stores the frozen base in 4 bits instead and trains a LoRA adapter on top. The paper's headline: a 65B model fine-tuned on a single 48 GB GPU while preserving 16-bit task performance. For a 4B-class model, the same idea moves the tune from "needs a big card" to "fits on a modest one".

LiveThree tricks: NF4, double quantisation, paged optimisers3 min▶

4-bit NormalFloat (NF4) is a 4-bit data type designed for weights that are roughly normally distributed, which pre-trained weights tend to be. It stores the frozen base at a quarter of 16-bit size (0.5 bytes per parameter against 2, the arithmetic from session 2). Double quantisation quantises the small scaling constants that 4-bit storage itself needs, saving a little more. Paged optimisers move optimizer state between GPU and CPU memory when a spike would otherwise run the GPU out of memory.

The adapter itself still trains in higher precision; only the frozen base is stored in 4 bits. That is why QLoRA can preserve 16-bit task performance in the paper's experiments: the part that learns is not the part that was squeezed.

Self-studyReading a memory table honestly3 min▶

Unsloth's requirements page gives minimum VRAM for QLoRA 4-bit and LoRA 16-bit: 3B 3.5 / 8 GB, 7B 5 / 19, 8B 6 / 22, 14B 8.5 / 33, 32B 26 / 76, 70B 41 / 164. It calls them "the absolute minimum" and suggests a batch size of 1 to 3 to use less VRAM. So a row is a floor at a small batch, not a comfortable working size. Longer sequences and larger batches push activations up.

Two more cautions. The table belongs to one library; other stacks use different amounts. And TRL's docs report Unsloth as "up to 2x faster with up to 70% less VRAM": that is a vendor claim quoted by TRL, reported, not something we measured. The Fine-tune your own Hermes walk-through ↗ runs Unsloth on Colab step by step; tonight we only read its numbers.

For prices to set beside the table: Hugging Face Inference Endpoints list an L4 24 GB at $0.80 per hour and an A100 80 GB at $2.50, H100 80 GB at $4.50 (list price read 2026-11-08, re-verify). Session 6 turns those into a monthly bill.

Real world

Guanaco, and the sentence people quote wrongly. The QLoRA paper reports that its Guanaco models reached 99.3 percent of ChatGPT's performance level on the Vicuna benchmark after 24 hours of fine-tuning on a single GPU. That is one benchmark, scored the way the paper scored it. It shows a 4-bit-base tune can be strong on that test; it does not show that a 4-bit model equals ChatGPT, and it says nothing about claim triage. Your eval is the only benchmark that answers Larkline's question.

Decide what ships: the merged model, the adapter, and the base beside it. Merging folds (alpha/r)BA into W so serving adds no latency. Keeping the untouched base model next to the adapter lets you compare, roll back, and re-train when the queues change. The Hermes walk-through ↗ gives the same advice: keep the stock model beside the tune.

★ Step 5 · what to keepKeep: the base model, unchanged, pinned by exact id and revision Keep: the adapter (A and B) as its own small artefact Serve: a merged copy W + (alpha/r)BA for production Why: roll back = point serving at the base again; re-train = new adapter on the same base, compare both.

Write the run card before the first run. One page that lets anyone, including you in three months, rebuild the exact tune and know which eval judged it.

Check yourself

Three questions

Clear all three and session 4 gets stamped in your passport.

1 · In PEFT's default LoRA setup, B is initialised to zero. What does that mean for a freshly attached, untrained adapter?

With B at zero, the adapter path adds nothing, so h = Wx exactly. That makes the adapter a safe no-op on day one and a quick pipeline check: the base and the untrained adapter should score the same. A gets small random values, so gradients still flow into B from the first step.

2 · A config sets r=16 and lora_alpha=16. What scaling does the adapter's output get, and what changes with use_rslora=True?

The PEFT docs give the scaling as lora_alpha/r by default and lora_alpha/sqrt(r) when use_rslora is True. Writing the scaling on the run card stops a quiet change of r from also changing how loudly the adapter speaks.

3 · A colleague says "LoRA cuts trainable parameters by 10,000 times, so our tune will be tiny." What is the fair reading?

Hu et al. 2021 report 10,000 times fewer trainable parameters and 3 times less GPU memory, for that one comparison. The ratio depends on model size, r and target modules, and memory falls far less because the frozen base and activations still sit on the GPU.
