The training set: where a tune is won or lost

The training run is the part everyone wants to talk about, and it is the part that matters least. A tune can only learn what the examples demonstrate, and an eval can only tell you the truth if the held-out rows never leaked into training. Tonight we write one example in the format the tools expect, see which tokens the model actually learns from, find a real leak in a well-known public dataset, compare four honest answers to "how many examples?", and clean and split Larkline's history so it is ready for session 4.

Part 1 · covers the format

One example, one demonstration

5 min live

A training example is not a fact you want the model to know. It is one demonstration of the exact behaviour you want back: this kind of input, answered in exactly this way. The tools agree on the shape. OpenAI's supervised fine-tuning guide asks for JSONL, one complete JSON object per line, each with a messages array of chat turns. Hugging Face's TRL SFTTrainer accepts the same conversational shape, and it also decides which of those tokens the model is graded on.

LiveThe shape: JSONL in chat format3 min▶

Each line of the file is one complete conversation: a system message carrying the instruction you would otherwise put in the prompt, a user message carrying the input, and an assistant message carrying the exact output you want. One line, one example. No trailing commas, no array around the whole file. OpenAI's guide uses this messages layout, and TRL calls the same thing a conversational dataset.

★ One Larkline example (constructed), shown wrapped; on disk it is one line{"messages": [ {"role": "system", "content": "Route the claim note to one of six queues. Reply with JSON only: {\"queue\": ..., \"urgent\": true|false}"}, {"role": "user", "content": "Phone stolen from my car last night, my bank card was in the case. Police report to follow."}, {"role": "assistant", "content": "{\"queue\": \"Fraud and loss\", \"urgent\": true}"} ]}

Notice what the assistant turn does not contain: no "Sure, here is the routing", no explanation. If the demonstrations are chatty, the tune will be chatty. Every example should be the answer you would accept in production, character for character.

LiveWhich tokens the model learns from2 min▶

TRL's SFTTrainer accepts two families of data: language-modelling data (plain text, every token is a target) and prompt-completion data, each in a standard or a conversational form. For prompt-completion data, its docs say the loss is computed on the completion only by default. For conversational data you switch the same behaviour on with assistant_only_loss=True. In plain words: the model still reads the instruction and the claim note, but it is only corrected on the answer.

That matters for small sets. If the loss also covered the prompt, a large share of the training signal would go into reproducing your own system message hundreds of times. Completion-only loss spends the signal where the behaviour is. TRL docs v1.17.1, read 2026-11-08; re-verify the flag names against the version you install.

Real world

The vendor format outlives the vendor. OpenAI's guide defines the chat-format JSONL above, and the same guide, read on 2026-11-08, says the platform "is no longer accessible to new users". The file format did not stop being useful: the same messages layout loads straight into TRL as a conversational dataset. Write your set in the plain chat shape and it moves with you to whichever trainer you end up on.

Part 2 · covers label quality, duplicates and leakage

A clean set, checked on real numbers

5 min live

Three problems quietly ruin training sets. Wrong labels teach the wrong behaviour with full confidence. Duplicates give some examples extra weight for no reason. And leakage, the same text sitting in both the training set and the held-out set, makes the eval report memory as skill. None of them is hypothetical: a short script on Banking77, a widely used public intent dataset, finds both duplicates and leakage in its official splits.

LiveWhy a leaked test row inflates your eval3 min▶

A held-out set exists to answer one question: how does the model do on notes it has never seen? A row that sits in both sets breaks that promise for that row. The tuned model has been corrected on that exact text, so getting it right shows recall of a training example, not the routing skill you are trying to measure. Every leaked row nudges the score up, and the nudge is not spread evenly: it lands on whichever queues the leaked texts belong to.

The damage is worst exactly when you compare arms, which is what session 5 does. A big prompted model never saw your training file; the tuned small model did. Leakage helps only one side of the comparison, so it can turn a tie into a "win". The fix is cheap and mechanical: normalise, match, and remove the shared texts from training before you train. Never remove them from the held-out set to make the numbers look tidy; the held-out set is the one you froze.

Self-studyLabels you can trust, and imbalance you can see3 min▶

Label quality. Constructed Larkline example: agents re-route about 1 in 20 notes later. If Priya trains on the first routing, roughly one demonstration in twenty teaches the wrong queue. Two moves help: use the final queue, not the first, and relabel a random sample to measure how often two careful people agree. The agreement number tells you the ceiling your eval can honestly report; a tune scored above human agreement is usually scoring the labelling style, not the task.

Imbalance. Banking77's train split runs from 35 to 187 rows per intent, while its test split is balanced at 40 each. A model trained on that shape sees some intents five times as often as others, and a balanced test set will then expose the rare ones. Larkline's urgent queue is the rare one by nature. Keep the imbalance visible in a count table before you train, and score per queue, not just overall, in session 5.

Duplicates. Four Banking77 train texts appear twice. That is harmless at this scale, but in a real support history, templated messages ("Please call me back") can repeat thousands of times and drown the rare cases. Drop exact duplicates after normalising, and look at the near-duplicates by eye.

Real world

A leak in a dataset everyone uses. Banking77 (Casanueva et al. 2020, arXiv:2003.04807, released by PolyAI under CC BY 4.0) has 10,003 training and 3,080 test examples over 77 intents. Running the normalise-and-match check on the full public splits finds 4 exact duplicate texts inside train and 7 test texts that also appear verbatim in train. Seven rows will not change a headline accuracy by much. The point is that the check took five lines, the dataset is carefully built and widely cited, and the leak was there anyway. Your own exported history, with copy-pasted templates and resubmitted claims, will usually have more.

Part 3 · covers how many examples and synthetic data

How many examples? Four answers, one honest method

5 min live

Ask five sources how many examples a fine-tune needs and you get five numbers spanning three orders of magnitude. They are not all wrong; they describe different tasks, different models and different definitions of "enough". Rather than pick a winner, line them up with their sources, then do the one thing none of them can do for you: measure your own curve on your own held-out set.

LiveThe four answers, attributed3 min▶

OpenAI's guide. A minimum of 10 examples; "We see improvements from fine-tuning on 50-100 examples"; "We recommend starting with 50 well-crafted demonstrations"; and "If 50 examples have no impact, rethink your task or prompt before adding training data." Read carefully, that is advice about where to start and when to stop, not a promise that 50-100 examples will be enough.

LIMA (Zhou et al. 2023, arXiv:2305.11206). A strong general assistant from only 1,000 carefully curated prompts and responses, with the argument that almost all knowledge comes from pretraining. That is a general-purpose chat tune; the lesson is about curation, not about the number 1,000.

Sibling paths. Learn Hermes AI session 94 ↗ advises 100-500 excellent examples for a behaviour nudge. Learn Prompt Engineering ↗ sets the bar at "thousands of examples and a stable task" before a tune beats a good prompt. Bertsch et al. 2024 (arXiv:2405.00200) add a measured caution: finetuning is more data hungry than in-context learning, though it can exceed long-context prompting with additional data.

The fair reading: the number depends on how narrow the task is, how good the base model already is, and how clean the labels are. Start small, double, re-score the frozen held-out set each time, and stop when the curve flattens.

Self-studySynthetic data: useful, with three known risks3 min▶

When labelled history is thin, teams ask a big model to write extra examples. It can fill a rare queue, but it carries risks you should name before you use it:

  • The teacher's mistakes are copied in. If the big model misroutes a kind of note, every synthetic example of that kind teaches the small model the same mistake, with full confidence.
  • Less variety than real notes. Generated text tends to be tidier and more uniform than what customers actually write: fewer typos, fewer half-sentences, fewer mixed-up claims. The tune then meets messier text in production than in training.
  • Leakage by the back door. If any synthetic example was generated from a held-out item, or paraphrases one, the held-out set is no longer unseen. Generate only from training rows, and run the overlap check again afterwards.

Keep synthetic rows tagged in their own column so you can train with and without them and compare on the held-out set. The held-out set itself stays real notes only.

Real world

The stop rule inside the vendor's own guide. The most quoted line from OpenAI's guide is the 50-100 range. The more useful line is the one after it: "If 50 examples have no impact, rethink your task or prompt before adding training data." Even the vendor that sold fine-tuning tells you that more data is not the default fix. A flat result at 50 is information about the task, and it is cheaper to learn at 50 than at 5,000.

Build-along

Clean and split a labelled set

★ 22 min · everyone builds

Constructed Larkline example. Priya exports 18 months of routed notes and turns them into three files. Follow along on any labelled CSV you have: a text column and a label column are enough. The code is the real check; any counts from Larkline are constructed and your numbers will differ. The only real counts on this page are Banking77's, labelled as such.

Normalise the text and drop exact duplicates. Lower-case it, strip it, and collapse runs of whitespace, then keep one row per normalised text. Keep the original text for training; the normalised key is only for matching.

★ Step 1 · normalise and dedupeimport pandas as pd def norm(s): # lower-case, strip, collapse whitespace return " ".join(str(s).lower().split()) hist = pd.read_csv("routed_history.csv") # text, final_queue hist["key"] = hist["text"].map(norm) before = len(hist) hist = hist.drop_duplicates(subset="key") print("dropped duplicates:", before - len(hist)) # Larkline's count is constructed; your numbers will differ. # On Banking77's train split this finds 4.

Check test-against-train overlap and remove leaked rows from training. If you already have a held-out file (Larkline labelled one after session 1), match on the normalised key and drop the matches from the training side only.

★ Step 2 · leak checkheld = pd.read_csv("held_out.csv") held["key"] = held["text"].map(norm) leaked = hist["key"].isin(set(held["key"])) print("leaked rows:", leaked.sum()) hist = hist[~leaked] # remove from TRAINING, never from held-out # On Banking77's public splits this finds 7 test texts in train. # Your numbers will differ.

Relabel a random sample and measure agreement. Draw a random sample, hide the agent's queue, and have someone who knows the queues label it again. Agreement is matches divided by sample size. Use it as the honest ceiling for any score you report later, and read every disagreement: they show you which queue boundaries are fuzzy.

Split train and validation, stratified by queue. Stratifying keeps the rare urgent queue present in every part. OpenAI's guide gives no fixed split ratio, only that the holdout should come from the same collected data with the same diversity; the 90/10 below is a starting choice, not a rule.

★ Step 4 · stratified splitfrom sklearn.model_selection import train_test_split train, val = train_test_split( hist, test_size=0.10, stratify=hist["final_queue"], random_state=20261108) print(train["final_queue"].value_counts()) print(val["final_queue"].value_counts()) # check the urgent queue appears in both

Write the JSONL in chat format. One line per example, the same system message on every line, the assistant turn exactly the output you want in production.

★ Step 5 · write JSONLimport json SYSTEM = ("Route the claim note to one of six queues. " "Reply with JSON only.") URGENT = {"Fraud and loss"} def write(df, path): with open(path, "w") as f: for t, q in zip(df["text"], df["final_queue"]): answer = json.dumps({"queue": q, "urgent": q in URGENT}) row = {"messages": [ {"role": "system", "content": SYSTEM}, {"role": "user", "content": t}, {"role": "assistant", "content": answer}]} f.write(json.dumps(row) + "\n") write(train, "train.jsonl") write(val, "val.jsonl")

Freeze the held-out set and never train on it. Record a fingerprint of the file so anyone can prove later that it did not change, and keep it somewhere the training script cannot read by accident.

★ Step 6 · freezewrite(held, "held_out.jsonl") $ shasum -a 256 held_out.jsonl > held_out.sha256 $ chmod 444 held_out.jsonl Rule written in the README: held_out.jsonl is scored in session 5 and never trained on, never used to pick settings, never "topped up".

Rerun steps 1 and 2 every time the data changes. New exports, synthetic rows and relabels all reintroduce duplicates and leaks. The check is cheap; a leak found after session 5 has already reported a score is not.

Check yourself

Three questions

Clear all three and session 3 gets stamped in your passport.

1 · With completion-only loss, what is the model trained on?

TRL's SFTTrainer computes the loss on the completion only by default for prompt-completion data, and assistant_only_loss=True does the same for conversational data. The prompt still shapes the answer; it just is not a target. A spends training signal reproducing your own instruction.

2 · Seven Banking77 test texts also appear in its train split. Why does that matter if you fine-tune on train and score on test?

A leaked row measures memory, not the skill. The effect on one headline number may be small, but it only helps the model that saw the training file, which is the arm you are trying to judge fairly. Remove the shared texts from training and keep the held-out set as frozen.

3 · A colleague says "OpenAI says 50-100 examples is enough, so we will stop at 100." What is the fair reading?

OpenAI's guide frames 50-100 as where improvements show up and 50 as where to start, and adds that if 50 examples have no impact you should rethink the task or prompt. LIMA, sibling advice and Bertsch et al. 2024 point higher for other tasks. Your own curve on a frozen held-out set settles it for yours.
